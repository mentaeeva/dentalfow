DentaFlow — MVP evidence pack

Technical assessment · 7 November 2026

MVP assessment scope

DentaFlow is a functional browser-based prototype for coordinating dental laboratory orders. The proposed benefit is a single order history across clinic, laboratory administrator and technician roles. This is a product hypothesis, not a measured customer outcome. The MVP contributes 40 points to the 100-point examination; no score is guaranteed.

Access and demonstration

Live URL: https://mentaeeva.github.io/dentalfow/ — clinic: moydent; laboratory administrator: alfa.admin; technician: erasyl. Demo password for all accounts: demo123. Use the same browser and origin when switching roles. Select English or Қазақша in the language selector. Use fictional patient identifiers and test files only.

MoSCoW priorities

MUST: create a valid order, assign a technician, complete work, send and confirm delivery, retain order history, English and Kazakh core journey, validation and role-specific views. These are required to demonstrate the coordination hypothesis. SHOULD: rework cycles, editable prices/rates, reports, keyboard access and persistent language choice; these support realistic exceptions and usability. COULD: richer analytics and document exports after validation. WILL NOT in this MVP: production authentication, real patient records, payment processing or a secure production file service. Supabase shared storage is available for fictional demo data only and requires separate security work before production use.

Architecture and deployment

Static HTML, CSS and vanilla JavaScript; no build step or server runtime. Supabase JS connects the browser to PostgreSQL and Storage when js/backend-config.js is configured; cloud.js loads and saves the shared demo state and uploads files. store.js implements domain transitions and local persistence; seed.js creates demo fixtures; views.js renders screens; app.js wires events. Data also keeps a localStorage copy under dentaflow-demo-v2; language uses dentaflow-language. GitHub Pages serves main /docs using relative asset paths and .nojekyll. Google Fonts is an optional visual dependency; system-font fallbacks remain available. Run locally with python -m http.server 8000 --directory docs, then open http://localhost:8000. A local copy provides a fallback if hosting is unavailable.

Five role scenarios and observed results

Method: automated JavaScript VM execution with isolated seeded data, plus interface checks where recorded. This is scenario-based technical testing, not a participant study. S1 Clinic: submit an order with a service, quantity and future deadline → RECEIVED. S2 Administrator: assign technician t1 → IN_PROGRESS. S3 Technician: view assigned work and complete it → DONE. S4 Clinic/administrator handover: send to delivery, reject unchecked confirmation, then confirm checked receipt → DELIVERED. S5 Administrator: open rework → new cycle, RECEIVED, previous cycle retained. All five domain scenarios passed. These checks establish execution correctness, not ease of use for actual customers.

Boundary and language evidence

40 locale assertions and 732 rendered screen variations passed across Russian, Kazakh and English. Additional checks passed for invalid quantities 0, -1, 1.5, 1000 and Infinity; valid form submission; unchecked/repeated receipt confirmation; another clinic’s UI visibility restriction; localStorage round trip; HTML escaping; and forward/reverse focus wrapping. See mvp-test-results.json for the saved execution results. VM checks do not substitute for browser layout, assistive-technology testing or linguistic review.

Evidence-linked iteration

I1 Technical finding: validateForm accepted fractional and unbounded quantities if input filtering was bypassed. Change: require integer quantity 1–999 with localized explanation. Verification: five invalid boundary values rejected and quantity 2 accepted. I2 Risk analysis: receipt handler relied only on the disabled button and could be invoked without all acknowledgements. Change: guard modal type, selected IDs, acknowledgements and clinic role; safely ignore repeat action. Verification: unchecked action preserves IN_DELIVERY, checked action reaches DELIVERED, repeat is harmless. I3 Accessibility finding: dialog keyboard navigation could leave the modal. Change: wrap Tab and Shift+Tab within visible focusable dialog controls, with a fallback for an empty dialog. Verification: forward and reverse wrapping passed handler tests. These three changes are tied to technical findings, not invented customer quotations.

Responsible design and material limitations

Role filtering is a demo interaction feature, not a security boundary: all demo data and passwords are available in the browser. There is no real authentication, encryption at the application level, or server audit trail. When Supabase is configured, the shared demo state and uploaded files persist across devices, but its open policies allow any visitor to read and change them. Clearing browser storage loses demo changes. Concurrent tabs can overwrite state; storage events synchronize snapshots but do not provide transactional conflict resolution. Storage failure shows a warning; it does not guarantee persistence. Existing input escaping reduces HTML injection risk, but this is not a security audit. Do not enter real patient or confidential information. Accessibility includes labels, focus styling, reduced-motion support and dialog keyboard wrapping; a full WCAG assessment has not been performed.
